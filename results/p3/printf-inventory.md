# printf at the machine level: inventory, the spec's shape, what is proved

PHASES `PrintfSpec_Statement`. Numbers from `scripts/printf_inventory.py`
(`results/p3/printf-inventory.json`) on the arena of `tcc -run sum.c` at the
cut (`scripts/tcc_cut.py --arena`, committed as `results/p3/sum-arena.tsv`:
77,864 bytes) and the replay trace `results/p3/sum-replay.json`.

## Where printf runs

tcc loads the libc.a/libgcc.a members P needs into its 4 MiB arena at
`0x86400000` and relocates them there: text `0x86400000..0x86410b68` (P's
136 bytes first, then the members, then tcc's PLT for the host system calls),
then data, then the PLT's GOT at `0x86412fb8..0x86413020`. Every member's
instruction words match the archive's on every unrelocated instruction
(placement by bytes, relocated instructions compared on their opcode), so the
arena code is the archive code with relocated immediates.

* `printf` at `0x86400148`, `_vfprintf_r` at `0x864001d4` (3,493
  instructions), the program's `_reent` at `0x86411b78`, its `stdout` FILE at
  `0x864128a8` (`Tcc/Printf/Sum/Layout.lean`, generated by
  `scripts/gen_printf_layout.py`).
* P's one call `printf("%d\n", 55)` (replay items 52..633): 1,657 steps,
  1,251 distinct instructions, 130 of them host code (`_write`, `_fstat`,
  `_isatty`, `_sbrk`, `memset`, reached through tcc's PLT).

`_dtoa_r` (1,532) and the bignum and soft-float routines for `%f %e %g`,
the wide-character routines for `%ls %lc`, `_malloc_r`/`_free_r`/`_realloc_r`.

## Reuse: none of ship-your-lua's stdio proofs apply

GNU ld relaxes `call` (auipc+jalr) to `jal` in ship-your-lua's ELF; tcc does
not relax. Every stdio routine that calls another therefore has different
instructions and offsets there (`_vfprintf_r` 3,395 vs 3,493 instructions,
`__sfvwrite_r` 311 vs 325, ...), and no at-lemma about it transfers. Only the
six leaf routines in the last row are word-identical. ship-your-lua's printf
work is also of a different shape: `_svfprintf_r` (snprintf's) specialised to
the bytes of one format (`%lld`, lane F1-FMT; `%p`, lane F1-24), on its
callee-context at-lemma layer (`gen_lua_at.py`, `Lua/Vm/Sim/Kit`), which is
specific to the Lua ELF and not part of this repository's port (`Vsa/` is the
import closure of the segment layer only). That one format cost about 2,000
hand lines, 6,768 generated lines and ~95,000 lines of segments.

## stdout is line buffered: the console alone is the wrong observable

In this image `_fstat(1)` reports a character device and `_isatty(1)` is 1,
so `__smakebuf_r` makes the program's `stdout` line buffered. A printf whose
output has no newline returns with its bytes in `stdout`'s buffer:

| program (on Sail, `tcc -run`) | console | exit |
|---|---|---|
| `c/tests/p3/linebuf.c`: `printf("%d", 42); _exit(7);` | (empty) | 7 |
| `c/tests/p3/linebuf_nl.c`: `printf("%d\n", 42); _exit(7);` | `42\n` | 7 |

So "printf appended `format …` to the HTIF console" is false for most formats.
The spec's observable is `stdoutBytes` = console ++ the bytes pending in
`stdout`'s buffer (`_bf._base .. _p`, none before `__sinit` ran), which every
call extends by exactly its output (`Tcc/Printf/Spec.lean`).

## The statement and why per image

`Tcc.Printf.PrintfSpec_Statement L init room` (open): from every `printf`
entry (`PrintfEntry`: format string at `a0`, at most seven variadic words in
`a1..a7`) with the code present (`CodeAt`: the arena text and GOT, the host
system calls), in a state stdio can be in (`StdioReach`: as the compile phase
left the arena data (`init`) with heap room, or after such calls, or after
the program's own stores outside printf's static data and heap), with stack
room, for every format and arguments in the integer subset (no float
argument, `%s` strings read from memory, at most nine digits per number,
output below `2^31` bytes), the call returns (`PrintfReturn`: back at `ra`,
`a0` the length, `sp` and callee-saved registers kept, `stdoutBytes`
extended by exactly `format`) with memory changed only in `Footprint`
(`stack` bytes below `sp`, the static stdio/allocator objects, the heap).

It is stated about the relocated code at its arena addresses, for this image.
The arena layout depends on the program (which members tcc loads, in which
order, where its data lands), so a load-address-parametric statement would
have to quantify over tcc's relocation of the archive bytes; the theorem it
serves is per program anyway. On P's call the stated footprint covers all
1,796 bytes the call writes (stack, heap, the `_reent`, `__sf`, the
allocator's state, the host's `brk.0` and `errno`; checked on the trace, not
in Lean: the replay's rows do not relate base memories across rows); the
stack bound is 4,096 (static frame sum along printf's call chains 1,216,
measured 992).

## What is proved instead of the general spec

* `Tcc.Printf.Sum.call0`: P's call is a `PrintfCall` of the image's newlib
  (entry at `0x86400148` with `"%d\n"` and 55, return to `0x86400074` with
  `a0 = 3`, callee-saved registers kept, `stdoutBytes` from empty to
  `"55\n"`), from the replay rows, every fact a kernel `decide`.
* `Tcc.Printf.machX`: an `ExtEnv` whose printf steps exactly on the calls an
  image makes (reached from reset, then a `PrintfCall`) with the image's
  return value and output; `machX_extDeterm`, `machX_model`
  (`PrintfModelOn ImgMakes`), and `imgMakes_of_spec` (the open spec makes it
  answer every call the image reaches in a stdio state).
* `Tcc.EndToEnd.tcc_run_sum_derived`: from reset, `tcc -run sum.c` halts
  printing `55\n` with exit code 0, and Clight's `sum.c` under `sumX` (the
  printf read off this image) prints exactly that and returns 0; no premise.

## What a general proof needs (not attempted)

Symbolic execution of `_vfprintf_r` over the format string: an invariant of
its main loop relating the parsed prefix, the `uio` array (up to eight
pending `iov`s, flushed by `__sprint_r`) and `ret` to `formatGo`; the flag,
width and precision parser (a jump table); the digit loops (decimal through
`__udivdi3`/`__umoddi3`, hex and octal by shifts); the padding loops;
`__sfvwrite_r`'s line-buffered path (`memchr` for the newline, `memmove` into
the buffer, `_fflush_r` → `__sflush_r`'s write loop → `__swrite` →
`_write_r` → the host `_write` → HTIF); the first call's `__sinit`,
`__swsetup_r` → `__smakebuf_r` → `_fstat`/`_isatty`, and `_malloc_r` with
`_sbrk`. About 1,000 instructions of `_vfprintf_r` and 1,500 of the helpers
on the integer paths, every loop with an invariant, at addresses no existing
proof covers, on a symbolic at-lemma layer this repository does not have.
